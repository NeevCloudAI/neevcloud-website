**Understanding Your Options: LoRA vs QLoRA**

Before writing a single line of training code, the most important decision is whether to use LoRA (Low-Rank Adaptation) or QLoRA (Quantized LoRA). Both are parameter-efficient fine-tuning methods that attach small trainable weight matrices to the frozen base model, dramatically reducing the number of parameters you need to update.

![](https://cdn.hashnode.com/uploads/covers/67a20ef8875434c6d881b8a5/43000708-2942-4a2d-965b-a617bb0633be.png align="center")

For most teams running on a single A100 80GB, LoRA in BF16 is the recommended approach for the 8B model. QLoRA opens up 70B fine-tuning on a single GPU, which is a significant cost advantage. The quality difference between LoRA and QLoRA is typically less than 1-2% on downstream benchmarks, making QLoRA the practical default for memory-constrained scenarios.

> **Why BF16 over FP16?**
> 
> BF16 (Brain Float 16) uses the same exponent range as FP32, making it far more numerically stable during training than FP16. The A100 has native BF16 Tensor Core support, delivering full throughput without the overflow risks common in FP16 fine-tuning of large models.

> **Step 2: Dataset Preparation**

The quality of your fine-tuning dataset has more impact on the final model than almost any other variable. A well-curated dataset of 1,000 to 10,000 high-quality examples consistently outperforms a poorly filtered dataset of 100,000 examples.

**Data format**

LLaMA 3 uses a specific chat template for instruction fine-tuning. Your data should be formatted to match this template, using the model's special tokens for system prompts, user turns, and assistant responses. The Hugging Face tokenizer for LLaMA 3 handles this automatically when you pass a list of message dicts.

**Dataset sizing guidelines**

![](https://cdn.hashnode.com/uploads/covers/67a20ef8875434c6d881b8a5/a53ff9e8-fab5-4301-adac-3ece9f085453.png align="center")

Always split your dataset into train (90%) and validation (10%) sets before training begins. Use the validation set to monitor overfitting, not as a tuning signal after the fact.

> **Step 3: LoRA Configuration**

The LoRA configuration determines how the adapter layers attach to the base model and how many parameters are actually trained. Getting this right matters both for model quality and for keeping VRAM usage within the A100's capacity.

**Key LoRA hyperparameters**

![](https://cdn.hashnode.com/uploads/covers/67a20ef8875434c6d881b8a5/0ea34df7-6100-433e-a08a-761e28dd6961.png align="center")

For the LLaMA 3 architecture, targeting all four attention projection layers (q\_proj, k\_proj, v\_proj, o\_proj) provides a good balance between adaptation capacity and training cost. Including gate\_proj and up\_proj from the MLP layers can help with tasks that require stronger knowledge adaptation, at the cost of ~15-20% more VRAM.

> **Step 4: Training with SFTTrainer**

The Hugging Face trl library's SFTTrainer is the recommended training interface for instruction fine-tuning on LLaMA 3. It handles chat template application, packing of short examples into full context windows, and gradient accumulation automatically.

> **Gradient Checkpointing**
> 
> Enabling gradient checkpointing recomputes intermediate activations during the backward pass rather than storing them. This reduces VRAM usage by 30-40% at the cost of ~20% slower training. It is particularly valuable for 70B QLoRA runs where every GB counts.

> **Step 5: Monitoring and Evaluating Your Fine-Tuned Model**

Training loss alone is not a reliable indicator of model quality. A model can overfit to training examples while producing poor outputs on new inputs. Robust evaluation requires task-specific benchmarks defined before training begins.

**Evaluation approach**

1.  Track validation loss at each epoch; look for the point where it plateaus or rises.
    
2.  Run human evaluation on 50-100 held-out examples from your actual use case.
    
3.  For classification tasks, report precision, recall, and F1 on a balanced test set.
    
4.  For generation tasks, use ROUGE-L or BERTScore in addition to human review.
    
5.  Compare your fine-tuned model against the base LLaMA 3 checkpoint on the same test set to quantify improvement.
    

Save adapter checkpoints at each epoch rather than only at training end. The best checkpoint by validation loss is often not the final one, particularly with smaller datasets where a few more steps can push the model into overfit territory.

> **Step 6: Merging Adapters and Deploying to Production**

After fine-tuning, you have two artifacts: the original LLaMA 3 base model weights and the LoRA adapter weights. For production serving, you can either load them separately at inference time or merge them into a single full-precision model checkpoint.

*   **Separate adapter serving**
    

Loading the base model and applying the adapter at runtime is the most memory-efficient approach during development and for A/B testing multiple adapter versions. The PEFT library handles this transparently.

*   **Merged model serving**
    

Merging the adapter into the base weights produces a standard model checkpoint with no runtime overhead. Use the PEFT merge\_and\_unload() method. Merged checkpoints deploy identically to the base model and are the recommended approach for production.

**Best Practices and Common Mistakes**

**What works**

*   Start with a small, high-quality dataset (500-1,000 examples) to validate your pipeline before scaling.
    
*   Use the LLaMA 3 chat template correctly; misformatted prompts produce unpredictable fine-tuning results.
    
*   Set a warmup ratio of 0.03-0.05 to stabilize early training, especially with small datasets.
    
*   Save checkpoints at every epoch and keep all of them until evaluation confirms the best one.
    
*   Evaluate against the base model on held-out data before considering any fine-tuning run successful.
    

**What to avoid**

*   Training past 3-5 epochs on datasets smaller than 2,000 examples; overfitting is the most common failure mode.
    
*   Mixing very different task types in one fine-tuning run without balancing the dataset carefully.
    
*   Using FP16 instead of BF16 on A100; the numerical instability is a known issue with large models.
    
*   Setting learning rates above 3e-4 for LoRA fine-tuning; aggressive rates destabilize training quickly.
    
*   Skipping validation set evaluation and relying only on training loss to judge training progress.

    **FAQs**
    
    **Can I fine-tune LLaMA 3 70B on a single A100 80GB?**
    
    Yes. Using **QLoRA (4-bit quantization)**, the 70B model fits within an A100 80GB and is suitable for production workloads.
    
    **How much training data do I actually need?**
    
    **500–2,000 high-quality examples** are usually enough for task-specific fine-tuning, while **5,000–15,000 examples** work best for domain adaptation. **Data quality matters more than quantity.**
    
    **How long does fine-tuning take on an A100?**
    
    **LLaMA 3 8B (LoRA)** typically takes **30–90 minutes**, while **LLaMA 3 70B (QLoRA)** takes around **3–6 hours** on an A100, depending on training configurations.
    
    **Do I need to use Hugging Face Transformers for fine-tuning?**
    
    **Hugging Face Transformers** is the most popular starting point for LLaMA 3 fine-tuning. Alternatives like **LlamaFactory**, **Axolotl**, and **Unsloth** offer more flexibility and faster training, while remaining compatible with **PEFT**.
    
    **How do I serve a fine-tuned LLaMA 3 model in production?**
    
    **vLLM** is the recommended framework for serving fine-tuned LLaMA 3 models on A100 GPUs, offering efficient inference and OpenAI-compatible APIs for easy deployment and integration.
